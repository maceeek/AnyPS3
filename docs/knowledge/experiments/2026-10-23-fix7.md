## START in game stopped the run — fixed (4d8b6a9)

**Verified (user runs):** four GUI runs on 2026-10-23 (`~/.local/share/anyps3-library/titles/BCES00511/runs/`
20261023T133222…, 133759…, 134006…, 134648…) end with `STOP pc=0x0068ff14 lr=0x0068ff7c: semaphore wait requires an
active scheduler`, r11=0x5c (92 = `sys_semaphore_wait`), r4=`0xffffffff80000000` (timeout in µs).
`anyps3/kernel_sync.py` only blocked a semaphore wait without a timeout and stopped on every timed one.

Fix: timed wait blocks with a deadline (kind 2 joins the scheduler's timed-wait wake-up in `threads.py`) and the retried
call returns CELL_ETIMEDOUT (0x8001000b) unless the semaphore became available, as RPCS3
`rpcs3/Emu/Cell/lv2/sys_semaphore.cpp:116-221` (local reference). New `sync_ext_deadline()` saturates `now + timeout`:
the game's timeout would otherwise wrap into an already expired deadline; mutex, event queue, lwmutex and lwcond used the
same unsaturated addition. Test: `tests/test_runtime_objects.py::test_timed_semaphore_wait_times_out_or_acquires`
(block/retry keeps deadline/ETIMEDOUT/saturation/acquire-after-expiry/scheduler wake), 3 targeted tests OK.

**Game (build 810 = `claude/fix7` 065c3e8, snapshot 810 = 805 + main's cloud follow-up + this fix):**

  `scratchpad/pause_probe.sh`): no semaphore STOP any more; the next draw stops the run:

  `input.pad_config`) are hidden unless "Show advanced, diagnostic and unavailable settings" is on; the schema now carries
  `supported` (installed source) besides `available` (active build), so a rebuild-enabled setting (render scale on an old
  build) stays visible with a "rebuild the title" hint. Timer slack, RSX threads and RSX memory cache are advanced.
- Import wizard: the key download / hex entry result is a colour-coded banner above the scroll area (✔ verified against
  the selected PUP/EBOOT, ⚠ format-only, ✖ failed — nothing changed) plus a non-blocking pop-up after a download.

### Stutter + precompile question — branch `fast2/fix7-stutter` (91e5fbf, 14a9049), no game build

- **Verified (user GUI logs; 805sb/sc/sd walking runs, exploratory, load 11–13):** the "stutter" is long stretches at
  2–20 FPS with the RSX worker busy 1.5–1.9 s per 2 s. Dominant cost: CPU NV3089 scaled blits of a GPU render target
  (960x704 tiled → 512x352 nearest), readback + ~15 ms CPU each, 2–3 per frame (300–500 ms/s), plus 50–180 ms/s readback
  waits. Second: cold shader work when walking into new areas (263 glslang compiles 6.0 s + 3.9 s pipeline creation in a
  2-min walk; one 2-s driver compile). The GUI env (`HOST_DRAIN=0`, `FLIP_EARLY=0`) is not the main cause (805sa).
- Fixes: 91e5fbf run-wise blit planner (CPU bench ~15 → 3–8 ms per level transfer; `ANYPS3_RSX_BLIT_RUNS=0` disables;
  differential tests vs. the per-pixel path, 3 mutations fail); 14a9049 shader disk cache cap 1024 files → 32768 files /
  4096 MiB (the cap evicted one session's own shader set).
- **Precompile answer (derived):** PPU/SPU are already translated ahead of time (RPCS3's PPU LLVM / SPU cache
  equivalent). What remains at run time is RSX shader translation, GLSL→SPIR-V (~23 ms each, disk-cached) and pipeline
  creation (warm: 771 pipelines in 42 ms per run). Boot-time pipeline prebuild would save only the warm cost; it cannot
  help unseen shaders (RPCS3 hides those with its shader interpreter). Real defect was the cache cap. Next: GPU-side
  surface-to-memory blits (avoid the readback), then asynchronous cold pipeline compilation with identical output.
