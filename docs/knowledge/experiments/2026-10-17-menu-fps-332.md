## Profile 331 in concurrent mode (verified; `local/ratchet/codex/batch/profile-331ts.md`)

- **Main thread**: only 3.3% of samples in translated PPU code. 44% memory protocol: `owner_scalar`
  (`anyps3/par_memory.py`) returns `nullptr` when `renderer_enabled`, so with the RSX worker **every** PPU load/store
  goes through `Lease::enter` (seq_cst, CAS on a broker cell), a store additionally `ScalarLock` + `bump_scalar`. 20% `engine_step`
  → `NativeSpuWorker::request/check/service` (the main loop calls the spu/rsx/audio tick every 256 PPU steps; supervisor
  mutex, 2× `steady_clock::now`, lock of each lane). 8% synchronous RPC main → RSX (store to a watched byte).
- Guest loop `0x696cf0–0x696d74` (function `0x696c10`) = waiting for the RSX fence: `mftb` + `sys_timer_usleep(30)`
  (`sc` 0x696d34, ~13,000/s); the main game thread therefore waits for RSX for part of the frame.
- **RSX thread**: draw 33%, `rsxgraphics::clear` path 21%, GPU fence wait 13%, idle 13%, RPC to the main
  thread 7% (`materialize_texture` → `notify_parallel`).
- Every syscall was printed to stderr (~20,000 write/s) and `std::thread::hardware_concurrency()` (sysfs) was called
  at every draw → fixed in 332 (trace history, `ANYPS3_TRACE_SYSCALLS=1` for live output; thread count cache).

## FPS drops in the menu (verified, 332ss/332ct)

- ~40% of 2 s intervals in the menu have 7–30 FPS (RSX thread 40–140 ms/frame). Samples assigned to intervals (332ss,
  300 samples): in slow intervals (< 25 FPS) 38% of the RSX thread is under the stack frame `rsx_clear_surface`, in fast ones 7%.
- Run 332ct with `ANYPS3_RSX_CLEAR_TRACE=1`: **0 CPU clears** (all clears via `rsxgraphics::clear`, without
  `clear_reject_*` in `ANYPS3_RSX_FALLBACK_STATS`, 332fs). The stack frames `rsx_clear_surface > Range::read/write >
  rsx_tiled_offset` are therefore calls from the GPU clear path (`Session::bind`) with omitted stack frames (tail call).
- **Derived (code `anyps3/rsx_graphics_codec.py` `load_pixels`/`commit_pixels`)**: upload/writeback of a surface between the GPU
  image and guest memory runs in 32 B groups (tiled) via `Range::read/write` — each group = `Lease`,
  spans, `LineLocks`, `bump_parallel`/`ReservationNotifications`. A surface of 960×704×4 B ≈ 84,000 groups → tens of ms.
  Matches the size of the drops. Handed over to RSXVK20 (follow-up task).

## RSX statistics in the menu (332fm, `ANYPS3_RSX_FALLBACK_STATS=1`, verified)

- Over ~52 frames (4096 draws): ~28 `flush_host_read` (readback of the GPU surface for the CPU, ~90 ms total), ~28
  `texture_invalidate_gpu_write` + `texture_miss` (render-to-texture via guest memory), ~105 `label_reader`
  (~170 ms). `menu_stats`: host_read 1.77 ms/frame, label_reader 2.93 ms/frame. The counts are similar in slow and fast
  windows — so the drops are not caused by the number of readbacks, but by the cost/contention (main `coordinator_ns` 20–60 ms).
- **Derived (code `rsx_graphics.py` `Session::synchronize_labels`)**: a CPU access to a page with a pending label
  performs a submit and **waits synchronously for the GPU** (`retire(true, through)`). The guest fence loop (0x696c10) therefore
  blocks on every poll. HW semantics allow returning the old value until the GPU label arrives (submit +
  non-blocking retire) — a candidate for RSXVK20b.

## Build pitfall: `python -m` picks up the live tree (verified, 2026-10-17 12:45)

- `PYTHONPATH=$SNAPSHOT python -m anyps3.build_game …` run from the project root imports `anyps3` from the **current
  directory** (with `-m`, the cwd takes precedence over PYTHONPATH), not from the snapshot. The `source_sha256` in `build.json` of builds 333, 333r,
  333p therefore differs from their snapshots (they contain the agents' work-in-progress files from the live tree); 332 is identical (the agents
  had not yet changed anything). **Conclusions from runs 333/333h/333r/333rh cannot be attributed to the intended combinations** — the deadlock
  (`RawPermit` vs. `wait_reader_gate`) arose in a mixed live tree (PAR9 in progress + RSXVK20 + PAR10 v8).
- Fix to the procedure: `python -P -m anyps3.build_game` (Python ≥ 3.11 `-P` = without cwd in `sys.path`) and after the build a check of
  `source_sha256` against the snapshot. The same for `python -P local/ratchet/tools/virtual_pad.py build`.
- PAR10b (interrupted by the main agent because of the faulty attribution) managed one change to `par_memory.py::notify_admission`:
  always lock the admission mutex and `notify_all` — removes the Dekker lost-wakeup (release store `active=false`
  of the reader vs. load of `admission_waiters`), which matches the captured stacks. Included in 334.

## Navigation: "regression" refuted — the game's auto-repeat (verified, 2026-10-17 15:20)

- RE of the input path (original game code): `cellPadGetData` from 0x65d92c (thread 1, 1× per frame) → the pad module
  remaps the buttons to an action mask (DOWN 0x4000, UP 0x1000) at 0xf6aa7c and an edge mask 0xf6aa74 (set for exactly
  1 frame); function 0x68d1f0 counts hold counters (UP 0xfa8efc, DOWN 0xfa8f00, …) and a tick every 0.1 s
  (`mftb`, constants 0x3dcccccd = 0.1 s and 1/79.8 MHz); dispatcher 0x68d314 sends an event on the edge and **auto-repeat
  when held for > 30 frames and a tick** (0x68d688–0x68d6a8). Verified by gdb breakpoint (`run_to_menu_ptrace.sh`,
  `libptracer.so`): 5 presses of 1 s each = 16 DOWN events (edge + 3–4 repeats).
- A 1 s press in the tests therefore yields 5–6 moves at 60 FPS in the wrap-around menu with 5 items → a seeming "0 or 1" move;
  at ~40 FPS (332) fewer repeats. **The behavior matches the original game, it is not a regression.** Diagnostic builds
  336a–336e (bisect, flip time, pad trace) served to refute it; 336d (flip time) fixed nothing and is not included.
- `nav_check.sh` now holds the button for `HOLD` (default 0.15 s = a tap). **335, 10 DOWN taps: 8 captured by the game
  (pad trace) and 8× a move of exactly 1 item**; 2 taps fell into a frame hitch (both the press and the release between two
  polls) — addressed by frame stability (PAR11/RSXVK21), on HW a short tap in a 250 ms stall would also be dropped.
