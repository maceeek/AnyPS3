# Split C++ translation and parallel compilation (256)

Date 2026-10-15, Claude Opus 5.5. Goal: the original ACIT menu and gamepad navigation —
**not yet reached**. This record addresses the main brake on development: a single ~458 MB
translation unit (LTO ~7–15 min, 255 not finished compiling).

## Change (verified tests)

- `anyps3/program.py`: `Program._parts()` shares one generator for both
  `cpp()` (a single TU, tests unchanged) and `cpp_units(units=N)`:
  `anyps3.hpp` (types, `PpuState`, pure instruction helpers FLOW/FLOAT/VECTOR/FS,
  declarations), `program.cpp` (runtime services, SPU dispatch, `anyps3_entry`, `main`),
  `ppu-NNN.cpp` (4 KiB pages), `spu-NNN.cpp` (TLS+MMAPPER+SPU core helpers
  + SPU functions). The units are split contiguously by cumulative size (≤ N files).
- Operations with `word==0` (imports, native module hooks, export redirects) and `sc`
  are emitted as external `anyps3_op_<address>(PpuState&)` in `program.cpp`;
  the page only calls them. The semantics of the body are the same (return from the op function → `break`).
- `anyps3/spu.py:generate_parts`: an SPU page with more than `SPU_FUNCTION_BODIES=1024`
  variants (PC × exact word from the image/overlays) is split into smaller PC ranges
  (`spu_image_I_page_P_SHIFT_CHUNK`) with a small dispatcher. The exact-word guard
  and the stop "SPU target has no static translation" are preserved.
- `anyps3/native_build.py`: `write_units` (+`units.json` with SHA-256),
  `unit_sources` (verifies the hashes), `compile_units` (parallel `c++ -c`, per-unit logs,
  link). All units use the same flags — the `PpuState` layout depends on `-DANYPS3_VULKAN`.
- `build_game.py --units` (default 96) writes the units instead of a single `program.cpp`.
- `local/ratchet/tools/virtual_pad.py build -j N`: for a split bundle it wraps only
  `program.cpp` (main) and compiles the other units unchanged; it deletes the `.o` files and keeps the logs.

Tests: `tests/test_split_units.py` (4): module import/export chain and syscall
result/unknown syscall across separate units; an SPU page with 2048 variants is
split into two 2 KiB halves and selects the exact words of both overlays, an unknown word and an
untranslated PC stop; a unit changed relative to `units.json` is rejected.
Whole suite: 229 OK with `ANYPS3_REQUIRE_VULKAN=1` (`local/ratchet/tests-256.log`).

## Limitations

Without LTO, import calls across units cannot be inlined (they are out-of-line,
negligible); the instruction helpers are `static` in the header and are still inlined.
The split does not change the game bytes or the profile.

Stop 253 (CollNarrow not translated) passed. New stop `pc=0x4eae98`, `lr=0x32b064`,
541,584,384 PPU steps: `SPU code differs from static image/overlays` — SPU `0x200`
at LS `0x7270`. Immediately before, the job manager loaded by DMA **CollBroad**
`0xb9bd80` (0xc680 B: 3×0x4000+0x680) to LS `0x100` and then **CollNarrow** `0xb8b180`

**Cause (verified):** profile 255 derived the jobs by the heuristic "starts with `ila`, ends
with a run of zeros". CollBroad was missing from it entirely and CollNarrow was truncated to 0x109a0
(inside the job there is a run of zeros `0xb9bb20–0xb9bb7f`, followed by a table and a trailer).

**Fix in profile 257:** `local/ratchet/tools/spu_job_overlays.py` — job start =
a 16-byte-aligned EA in `0xb00000–0xbf4480` that is pointed to by a 32-bit word in the original
PT_LOAD (e.g. the EA/name pair at `0xca1478`: `0xb9bd80`→"CollBroad" `0xac2638`,
`0xb8b180`→"CollNarrow" `0xac2648`), the first four words are `ila` and a zero
quadword precedes it; the range extends to the next start (trailing zeros trimmed). Result: 138 jobs
(previously 128; all 128 old starts are referenced, none shrank, 10 added,
123 extended), 978,720 B. Rejected references into code: `0xb62010`, `0xb900d0`,
`0xbce090`. The script verifies the observed DMA ranges of both jobs. The trailer formats differ
(`ffffffff X 0 ffffffff` only for 30 jobs), therefore the end is not determined by the trailer.
Backup `local/ratchet/profile-before-spu-jobs-257.json`, log `local/ratchet/profile-spu-jobs-257.log`,
profile SHA256 `14f7590e…`. Build 257: 4 min 9 s.

## Run 257 and stop (verified)

Stop 256 passed (CollBroad/CollNarrow executed). New stop `pc=0x202a9a4c`, `lr=0x202a99d4`,
541,769,959 steps: `unmapped or split guest memory access address=0x202b0c00 size=128 write=0`.
Instruction `0x7d20f828` = `lwarx r9,0,r31`, r31 `0x202b0c2c`; the module with code `0x202a0000+0xb6b0`
and data `0x202b0000+0xc38` (RW). The runtime computed the reservation token via `access(line,128)`, but the granule
`0x202b0c00–0x202b0c7f` extends past the end of the segment. Architecturally `lwarx` reserves the granule,
but accesses only the loaded word.

Fix (258): `GuestMemory::reservation_token(address,size)` (`anyps3/runtime.py`) — only the bytes that are read must
be mapped; the token tracks the host lines of the granule; if another guest region intersects the granule
(writes would escape tracking), an explicit stop. `flow.py` lwarx/ldarx/stwcx./stdcx. use this
variant, SPU `getllar/putllc` remain at the full 128 B. Test
`tests/test_memory.py::PartialGranuleReservationTests` (original instruction, reservation success/loss,
write in a different granule, ordinary access past the segment still faults, token match with the 128 B form, shared granule = stop).

At the same time in 258: the codex subagent implemented `_sys_printf/_sys_vprintf/_sys_snprintf/_sys_vsnprintf`
according to firmware 3.01 liblv2 (`local/ratchet/codex/printf-result.md`, `anyps3/guest_printf.py`,
`tests/test_guest_printf.py`). Whole suite 240 OK (`local/ratchet/tests-258.log`).
