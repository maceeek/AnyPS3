## Cause analysis (verified by reading the generated code of build 380)

- **PPU** (`native-bundle-380/ppu-043.cpp` `page_556`): every instruction calls `anyps3_ppu_step` (write of `state.pc`,
  comparison/increment of `state.steps`, trace test), registers are in `state.r[]`, every load/store goes through
  out-of-line `GuestMemory::load/store_parallel_inline` with the concurrent protocol (Lease/hazard/ScalarAccess,
  ~30% of PPU time in the 380load profile). The measurement overhead of `ExecutionPpuPage` reads the clock on every entry into a page
  (`PERF CLOCK owner=execution reads_total` ~1.4 billion, vDSO ~7.6% of PPU samples) — it distorts the measurement as well.
- **SPU** (`spu-031.cpp` `spu_image_0_page_7_8_71`): "static interpreter" — for every instruction an interrupt check,
  loading a word from LS and a `switch` over all variants of the word at that address, `t.pc`, block counter; byte-wise operations.
  `spu_single_vector` (exact SPU FP) ~20%, polling of `spu_collect_events` ~9%.
- **RSX**: ~39 µs CPU/draw spread out (driver 9%, memcpy, snapshot of guest pages, mprotect, heap, hash lookups).

## Critical path: the main thread waits for the SPU (sampler 380load + EBOOT disassembly)

**Verified** (guest PC of the main thread's samples in the window `sample-profile-380load-T1..T2`, 96,209 PPU samples;
`llvm-objdump --triple=powerpc64` over `local/ratchet/EBOOT.analysis.elf`):
- `0x5564c0–0x556540` **~15.7%**: function `0x5564d4` (callers `0x67a818`, `0x686fe4`, `0x92a614`) waits until
  `(int16)*(r3+0x18) < 0`; the loop body is 34× `or r31,r31,r31` (Cell PPE priority/delay hint, semantically a no-op).
- `0x666060–0x6660c0` **~8.7%**: delay function `0x666068` (CTR = (r3+15)/16+1 × a block of 16× `or r31,r31,r31`),
  called among others from the wait for the engine counter `0x696d50` (`delay(256)`).
- `0x696d00–0x696e10` **~4.4%**: wait for the engine counter (PIPE2): according to `mftb`, during the first 0x137b8 ticks (~1 ms) actively
  via `delay(256)`, then `usleep(30)` (`sc` 141 at `0x696d34`), after ~5 s it calls `0x696668`.
**Derived:** ~28% of the main thread's PPU time is guest busy-waiting; together with `main_idle` of ~18 ms this makes ~28 ms
of the ~66 ms frame spent waiting for SPU jobs to complete. The real PPU work is ~30 ms/frame. For 60 FPS the latency of
SPU jobs is therefore just as critical as PPU instructions. Per-thread SPU: `0x100` ~93% CPU (23.7% `spu_collect_events`),
the SPURS workers `0x2000200`/`0x3000200` have 46–57% of samples on LS page 0x0 (probably kernel/idle polling).
Handed to SPUFAST and PPUFAST.

Design: 4 GiB `PROT_NONE` reservation, guest maps via `mremap` from a coherent memfd alias (the same physical pages);
a table of 1 B/4 KiB (no_load/no_store/claimed/observed/tracked/dirty); inline only within the map owner's "section"
(PPU thread), writers of blockers wait via membarrier + odd sequences; outside the section the code sees the all-blocked table.
Registers in block locals with write-through (the state is architecturally current after every instruction → exceptions without
a landing pad). The hard step limit is per block; the exact cut/trace only in the diagnostic build (`trace=True`).
Instructions/frame increased due to spin-waiting for the SPU. New largest overhead: `ppu_schedule` every 4096 steps
(coordinator 9.6 ms/frame). Limitations: only the PPU has the inline path; watch/dirty bits without quiesce (derived
equivalence with the earlier compact path, TSan not run). The agent did not run the whole suite over the tree.
