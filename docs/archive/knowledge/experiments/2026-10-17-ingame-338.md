- `journalctl --user`: at 17:07:23 systemd-oomd killed `app-org.kde.konsole-…/tab(2146).scope` (RAM 66.9/67.0 GB,

  `native-virtual-338/objects/` remained empty; build 338 was never compiled.
- Repeat in a scope (`anyps3-build-338r`, `MemoryMax=32G`, −j12): **oom-kill after 45 s, peak 32 G**.
- One TU (`ppu-000.cpp`, textually identical in 337 and 338; only `anyps3.hpp` differs), measured via cgroup `memory.peak`
  / journal "memory peak" (`/usr/bin/time` is not on the system):
  - 337: **1.0 GB, 23.7 s**;
  - 338: **> 10.7 GB and > 105 s**, still growing (terminated);
  - 338 + `load/store_parallel_inline<Size>` as `[[gnu::noinline]]`: 2.1 GB, 106 s;
  - additionally `load()`/`store()` back without `[[gnu::always_inline]]` (as in 337): **1.0 GB, 24.0 s**.
- **Cause (verified by the measurements above, mechanism derived):** PAR12 forced inlining of `ScalarAccess` (try/catch,
  non-trivial destructors `~ScalarAccess`/`WriterHazard` → cleanup landing pads, several atomics and broker/observer calls)
  into every guest load/store in the translated functions; `always_inline` on `load()`/`store()` additionally inlined the serial
  path as well. Fix in `anyps3/runtime.py` (snapshot **339** = 338 + only this file): the PAR12 fast path stays unchanged
  in semantics, just one out-of-line copy per width in each TU. Performance (ns/instr, FPS) must be measured again in the game.
- Lesson: **every compilation, suite and run in its own `systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0`**,
  not concurrently with other memory-heavy work; when changing inline helpers, measure a single TU before the full build.
